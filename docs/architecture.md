# Architecture — evolve the working app, connect real state incrementally

Updated 2026-10-02. Course adaptation is now owner-authorized. Keep one Next.js application at `apple-music-clone/`, the existing lockfile, only `main`, and the `J:\courses` checkout alias. No replacement scaffold, branch/worktree fleet, framework migration or speculative service architecture. The music routes and immutable reference archive remain reproducible; unchecked parity is not newly accepted.

## Current implemented boundaries
`app/learn` contains Server Component routes and metadata; async route parameters and search parameters are awaited. Public course metadata comes from `lib/platform/catalog.ts`. `lib/platform/lesson-content.server.ts` uses `server-only` and selects only deliberately public demo lesson content. A paid, non-preview lesson is not delivered just because browser state claims access. This is a demo visibility policy, not implemented production authorization.
`components/platform` contains bounded client islands for shell navigation, saved courses, progress, notes, local posts and replies. The shell receives server-rendered children; it does not require every route to become a client component. `platform.module.css` owns scoped adaptation tokens and component styling. Music still uses its original component switch and state model; course actions must not mutate music scenes.
`preview-state.ts` validates a versioned browser-state projection; `preview-store.ts` supplies stable external-store snapshots and a deterministic server snapshot. State is confined to this browser and is not an account, enrollment, order or security boundary. Unknown versions and unreadable data remain untouched and read-only; blocked storage gets a disclosed memory-only fallback; write failures preserve previous saved data.
The additive v1 replies field accepts older data without rewriting it on read. Replies have real known parents, bounded IDs/text and a minimal projection. Limits are 40 posts, 80 replies, 6,000 characters per note and 400,000 serialized characters overall. These are local prototype limits, not a backend retention or concurrency policy. Note conflict checks detect a changed saved value before a local save; localStorage does not provide cross-tab transactional guarantees.

## Backend decision: next integrated slice, not the last layer
Keep the reviewed frontend now; implement the real free-course backend journey next, before adding commercial selling or an unbounded set of mock screens. Start with verified identity, creator ownership, publication, idempotent free enrollment, authorized lesson access and durable progress/notes/community. Do not pretend that browser persistence is that backend.
Candidate default: managed PostgreSQL with Supabase Auth/database/storage, Next.js server-only data access and SQL migrations. Stripe hosted Checkout/Connect and a private managed media provider remain candidates for later verified integrations. They are not currently configured. Recheck current provider docs, region, costs, account/project identity and existing resources before choosing or creating anything. Paid provisioning and public release need approval; never adopt an arbitrary connected project.
Use a small server-only data-access layer around actual use cases, not generic repositories, a second ORM migration authority, microservices or a client SDK with privileged keys. Server Components read safe projections directly. Server Actions and Route Handlers independently validate input, verify server identity and authorize the exact object/action; hiding a button or checking a layout is insufficient.

## Data and authorization invariants
Represent users, creator workspaces, workspace ownership, courses, ordered lessons, draft revisions/publication, source-specific access grants, progress, private notes, discussions, replies and moderation actions explicitly. Keep stable opaque IDs; public slugs are not identity or authorization. Enforce course/lesson and post/reply relationships with database constraints and application checks.
Every protected lesson-body, media, transcript and resource read uses the same authoritative access policy. Bookmarks, completion records, role strings in localStorage and checkout-return URLs grant nothing. Public catalog DTOs exclude protected content, private notes, tokens and payment data. Never cache one user's private response as public catalog data.
Use database row-level policies as defense in depth where supported, plus object-level checks in the server layer. Test learner A versus B and creator workspace A versus B with their real user sessions, not only an administrative service key. Keep privileged keys server-only; never expose them via public environment variables or logs.
Free enrollment should be idempotent under concurrent requests. Progress distinguishes last position, explicit completion and latest resume; notes/drafts use revision checks so stale writes return recoverable conflicts. Cross-device persistence is an acceptance test, not something a local success toast proves.

## Publishing, community and money
Creators edit owned drafts; submission locks a revision for review. Publication exposes a deliberate public projection and preserves lesson IDs. Ordinary unlisting stops new discovery/sales without silently revoking valid access. Suspension is a separate, attributable action with support and remedy policy. Use the detailed requirements in `data-model.md`, `security-and-trust.md` and `commerce-and-video.md`, subject to the current phase decision.
Real discussions and replies require course visibility, author attribution, write permission, abuse limits and report/hide/restore behavior. Private learner notes never become community posts implicitly. Do not send notifications until delivery, privacy, preferences and retry behavior are implemented and approved.
Paid checkout uses server-owned prices and provider verification. Fulfillment must handle duplicate, concurrent, delayed and out-of-order events with idempotent order/access effects. Access depends on authoritative grants, never the redirect. Refunds and revocation follow a defined policy; do not erase learning records to reverse a charge. Sandbox payment success is not live-release eligibility.

## Test and migration strategy
Keep fixture-backed UI tests, pure domain tests and actual integration tests distinct. A mocked user or in-memory grant is not proof of isolation. The first integration milestone uses two separate test accounts: one creator publishes a free course; another learner enrolls, reads, records progress/notes, asks a question, leaves and resumes in a second browser. Include denied cross-user/workspace reads and writes, stale revisions and duplicate enrollment.
Do not automatically upload browser notes/posts to an account when authentication arrives. Propose an explicit, user-visible migration with validation, conflict handling and privacy choices. Preserve local data until migration has succeeded and the user has chosen what to import.
For platform-only work run the platform domain/browser suites, typecheck and optimized build checks. Changes to root CSS, shared music state or the old shell additionally require the reference corpus. Record actual source identities and keep production checks separate from development. See `development.md` and `style.md`.

## Complexity budget and source basis
Add durable queues, dedicated search, subscriptions, teams, AI, live events and complex versioning only against a concrete problem and a complete testable slice. Correct access and recovery come before a large inventory of disconnected screens. Current implementation has no provider credentials, authentication, purchase processing, live community or deployed backend.
Official Next.js authentication/data-security and React external-store documentation were consulted through Context7 on 2026-10-02; source URLs and limitations are recorded in `research.md`. These guide server/client boundaries and stable hydration; they do not certify this prototype's production security.
